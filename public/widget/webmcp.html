Page tools for browser assistants

How this site offers tools to an assistant in the browser, and how the tutor limits the tools on the server.

What WebMCP is

WebMCP is a proposed way for a web page to offer tools to an assistant that runs in the browser. The page calls document.modelContext.registerTool. The assistant can then see the tool and run it.

In Chrome today this needs a testing flag. Use Chrome 146 or later. Open chrome://flags/#enable-webmcp-testing, set it to Enabled, and relaunch Chrome.

The assistant does not have to be one this site built. Gemini in Chrome can call the tools. A browser agent can call them. The Model Context Tool Inspector extension can list them and run them by hand.

What each page offers

The read-only tools do not read cookies, web storage, or saved chat. The color tools are the only ones that change the page, and they change only the example color.

Every page offers get_site_guide. It lists the public pages on this site. It returns the path, the title, and a short summary for each page. The home page summary says that sign-in is needed to see what the browser reveals.

The signed-out home page also offers get_landing_guide. It says you need to sign in before this site can show what the browser reveals. It returns the public links on that page. It does not read the browser.

The signed-in tutor also offers get_browser_reveal and get_connection_reveal. They repeat what the probe page already shows. Cookie values stay hidden. Each one returns that public view.

The gotchas page also offers get_atlas_summary, lookup_atlas_technique, and lookup_gotcha. ATLAS is the Adversarial Threat Landscape for Artificial-Intelligence Systems from MITRE. The lookup returns the public lesson. It does not include attack steps.

You can give get_atlas_summary a status to keep one group. The groups are fixed, mitigated, accepted, needs-human, and not-applicable. Omit status to list every technique. not-applicable means the techniques that do not apply to this site.

The lookup tools take a code or words from the name. If you give both, id wins. The result includes a short note when that happens.

The architecture page also offers get_architecture_guide. It describes the four diagrams. You can pass req, auth, loop, or trust. Omit the section to get all four. It returns the title and summary of each diagram.

The live demos page also offers get_demo_catalog and read_demo_state. The catalog is a fixed list. Omit the demo code to list all of them. The state tool says whether a demo is on the page and whether a result is on screen. It does not return that text. While the list is still loading, the state says so. The script injection lab counts as on the page.

The widget docs pages also offer get_page_guide. It returns the headings and the links on the page you are reading.

The widget home page also offers set_color, get_color, and reset_color. They change or read the example color on that page and nothing else. The swatch starts at #1f6feb. #3366ff is only a sample in the tool form. Each tool returns the color now on the swatch. The color field description is short. The allowed color names stay in the schema list. A bad color returns an error, and that error includes the allowed names.

One tool definition, two callers

Each tool is written once. WebMCP registers that same object with document.modelContext.registerTool.

The chat widget on these docs pages can use the same object when you are connected to OpenRouter. The widget reads the list and sends the tools with your question.

Some fields exist so the Model Context Tool Inspector can show a sample input. Those fields are annotations, examples, and oneOf. outputSchema documents the result for tests and for future browsers. Chrome 156 does not pass outputSchema on. It is absent from getTools(). The page tools do not set default. A default made the inspector send a value even when leaving the field out would list everything. The color tool still has a sample default so a manual run can fill a color. That sample is #3366ff. It is not the starting color. The starting color is #1f6feb. The widget removes these extra fields before the call reaches OpenRouter. OpenRouter receives the tool name, the description, and a simpler input schema.

Why the tutor chat does not go through WebMCP

The tutor on the main site runs on the server. When the model asks for a tool, the server runs that tool itself. It does not ask the browser to look the tool up through WebMCP.

The widget does the same kind of thing in the page. When OpenRouter asks for a tool, the widget calls the tool function directly.

WebMCP is the door for an assistant this site does not own.

When a server-to-page bridge makes sense

A bridge makes sense when the server agent needs a power that only the server has, and also needs to change or read the open page. It also makes sense as a lesson, so you can see both sides of one call.

This site does not have that bridge yet. Here is how it would work.

  1. The server would define a custom tool with the same name as the page action.
  2. That name would have to be added to the allowed tools list, called ALLOWED_TOOLS in the server code. The permission handler would reject it otherwise.
  3. The tool would need a strict input schema. The page would check the input again before doing anything.
  4. The server would send the call to the open tab on the chat stream.
  5. The page would run the action and post the result back. The server would give that result to the model.

render_widget is the one-way version that already exists. The server tool emits an event. The page draws the chart. The page does not post a tool result back for the drawing itself.

How the Copilot software development kit limits tools

The limits are already written up as gotchas. This page does not repeat them. It only points at them.

The client runs in empty mode, so the built-in shell and file tools are not available. Each session offers only custom tools. In the kit that setting is availableTools set to custom:*. Read Never run the SDK in its default mode on a shared server.

A permission handler runs before each tool. It denies the request unless the kind is a custom tool and the name is on the fixed list of ten. Read Every tool call goes through the permission handler: deny by default.

Each tool checks its input again inside its own handler. A name that passed the list can still be rejected if the arguments are wrong.
