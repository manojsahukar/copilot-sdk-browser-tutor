Why a client-side key is an XSS risk

Because the OpenRouter key lives in sessionStorage, it is readable by any JavaScript that runs on this page's origin. If an attacker could inject a script — a cross-site scripting (XSS) bug — that script could read btw_or_key and spend your OpenRouter credits. This is the honest trade-off of a backend-free, bring-your-own-key design.

Who bears the risk

The exposure is the visitor's own key and credits, not the site owner's. There is no shared server key to steal, and no other visitor is affected. Still, the site must avoid XSS, because an injected script on this origin can read the key.

How the widget reduces it

The pilot pages ship a strict meta-tag CSP (script-src 'self', no unsafe-inline, no eval), so injected inline scripts will not run. Model replies are rendered through marked + DOMPurify, so a prompt-injected answer containing <script> or <img onerror> is neutralised, never executed. A meta CSP cannot set frame-ancestors or report-uri, so clickjacking protection still needs a real header on hosts that allow it.

Keys in client-side storage are convenient and backend-free, but they are only as safe as the page is free of XSS. Treat the key as the visitor's to protect.
